## Deployment (2026-08-30, CEO: "deploy to netlify… try hugging face… best free method")
- **D-17 — Netlify cannot host the backend** (no Python runtime for a ~1.5 GB torch stack; functions cap ~250 MB). Split deploy: frontend on Netlify, model on Hugging Face. Render free (512 MB) OOMs on ViT; Railway/Fly need cards — HF is the only free host that fits.
- **D-18 — HF free tier changed: Docker Spaces are Paid, free = Gradio SDK on ZeroGPU** (tooltip: "Subscribe to PRO for cpu-basic"). The prepared Docker/Flask bundle was shelved (kept in `deploy/hf-space/`); the Space is a pure Gradio app exposing `classify(image) → top-3` — the officially supported free pattern, lowest demo risk.
- **D-19 — Frontend became dual-mode behind one `api.ts` interface.** Default build = local Flask (`/api/...`), unchanged for the internship demo. `VITE_SPACE_ID` build = recognition via `@gradio/client`; search + nutrition scaling run fully client-side from the bundled `data/*.json` (they were static data all along — no server needed). Confidence thresholds 0.70/0.35 mirrored in `src/lib/nutrition.ts`.
- **D-20 — Two Space build failures, both fixed by requirements:** (1) transformers 4.45 pins `huggingface-hub<1.0` vs gradio 6.26 needing `>=1.16` → unpinned to `transformers>=4.57` on the Space only (local stack stays 4.45); (2) modern transformers' AutoImageProcessor requires torchvision → added. Local repo keeps its own pins — the Space has its own tiny `deploy/hf-space-gradio/requirements.txt`.
- **D-21 — No credentials ever touched:** HF auth = the CEO logged into Chrome themselves (one human step); Netlify used the CLI token already on the machine. Space + site both created under the CEO's own accounts (mansourismatic / MohamedMansourii's team).
- **D-22 — Tunisian foods added as data, not model classes (CEO: "add couscous, marga, loubia, mloukhiya, ejja, etc.").** The ViT only knows Food-101 and no free Tunisian-food model exists, so 16 dishes (couscous, marga, loubia, mloukhiya, ojja/ejja, lablabi, brik, kafteji, tajine tunisien, chorba, méchouia, chakchouka, merguez, fricassé, makroudh, bambalouni) were added to `foods.json`/`nutrition_table.json` with French + Arabic-script aliases. They're reachable via the FR-05 correction search (placeholder now hints "couscous, ojja"); on the deployed app they work with **zero Space changes** because search/nutrition are client-side. All rows `needs_review: true` — the CEO is the best reviewer for these. Recognition of a Tunisian plate still returns the closest Food-101 guess (usually low-confidence), which is exactly the flow that surfaces the search.

## Tunisian recognition (2026-08-31, CEO: dataset links + "Both")
- **D-23 — Dataset triage from the 7 links the CEO sent:** kept pfemrds/detection-tunisian-food-2025 v5 (1,208 imgs, 11 clean classes, best model 84.6% mAP50), mariems/tunisian-food-seg v3 (1,902 imgs — weak model but rich labels: ojja/merguez/bambalouni/makroud/tajine/kafteji) and working-llaze/dataset-tn-annotated-exemples-2 (1,000 imgs, 10 classes). Rejected: karim (275 imgs / 212 junk classes), pfa-wfua5 (16.6k mixed-cuisine mega-dump, multi-GB for marginal gain), pfa-cpnnl (likely same-source images as pfemrds → train/val leakage risk). All kept sets CC BY 4.0. Excluded classes: ingredients (fish/chicken/egg/lamb/thon/vegetables), "coktail hlou" (drink), "Kskrout kafteji" (sandwich variant ≠ kafteji plate).
- **D-24 — Own classifier over Roboflow-hosted-only:** MobileNetV3-Small fine-tuned on 9,280 train / 2,381 val crops (bbox+15% pad + full-image-by-largest-box, cross-dataset hash dedupe) → **val top-1 86.7% / top-3 96.0%** over 19 dishes, 6.3 MB weights, published to hub (mansourismatic/tunisian-food-classifier). The Roboflow serverless detector stays as an optional third engine behind the ROBOFLOW_API_KEY secret (CEO adds it; never in chat). Open-set merge policy: Tunisian leads at ≥0.85 always, ≥0.55 only when ViT <0.70; candidates <0.35 dropped; mirrored in backend/tunisian.py and the Space.
- **D-25 — Space inference moved to CPU with a decorated ZeroGPU placeholder.** Live testing hit "ZeroGPU runs limit" — anonymous visitors carry a small GPU quota, a mid-demo death sentence. CPU ViT ≈ 1-1.5 s (FRD allows "a few seconds"); a never-called @spaces.GPU function satisfies the runtime's startup check. Reliability > 4× speed for a demo.
- **D-26 — ToS + downloads were CEO-approved explicitly** (Roboflow ToS acceptance and the dataset zips); zips deleted after extraction, tn_datasets/ (~1.5 GB incl. 11.6k crops) deleted after training — per the storage law and the disk-pressure coordination note from the yt-factory session.
